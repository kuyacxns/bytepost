Kubernetes 1.36: Mixed Version Proxy wird Beta

Die Mixed Version Proxy (MVP) wurde in Kubernetes 1.28 als Alpha-Funktion unter dem Feature-Gate UnknownVersionInteroperabilityProxy eingeführt. Das Ziel war einfach, aber kritisch: Cluster-Updates sicherer machen, indem Anfragen für Ressourcen, die noch nicht im älteren API-Server bekannt sind, korrekt an einen neueren Peer-API-Server weitergeleitet werden, anstatt einen falschen 404-Not-Found-Error zurückzugeben.

Wir sind begeistert, bekannt zu geben, dass die Mixed Version Proxy in Kubernetes 1.36 in die Beta-Phase eintritt und standardmäßig aktiviert wird! Die Funktion hat sich seit ihrer ersten Veröffentlichung erheblich weiterentwickelt und wichtige Lücken geschlossen.

Was ist das Problem, das wir lösen?

In einem hochverfügbaren Control-Plane, das ein Update durchläuft, gibt es oft API-Server, die unterschiedliche Versionen ausführen. Diese Server können unterschiedliche Satz von APIs (Gruppen, Versionen, Ressourcen) anbieten.

Ohne MVP gibt der API-Server, wenn ein Client eine Anfrage für eine Ressource sendet, die er nicht kennt (z.B. eine neue API-Version, die im Update eingeführt wurde), einen 404-Not-Found-Error zurück. Dies ist technisch gesehen falsch, da die Ressource im Cluster verfügbar ist, aber nicht auf diesem spezifischen Server. Dies kann zu schwerwiegenden Nebenwirkungen wie einer falschen Garbage Collection oder blockierten Namespace-Löschungen führen.

MVP löst dieses Problem, indem es die Anfrage an einen Peer-API-Server weiterleitet, der die Ressource anbieten kann.
